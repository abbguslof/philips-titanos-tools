## `sys_run` and the update environment

`sys_run` is a gzip tar (5,176,607 stored bytes, 19,005,440 decompressed). It
contains:

| File | Size | Role |
| :--- | ---: | :--- |
| `run.sh` | 954 | Entry point |
| `ndp_preinit.ko` | 12,151,296 | eMMC/pre-init module |
| `ndp_gfx.ko` | 5,808,720 | OSD module |
| `stty` | 293,396 | Copied to `/bin` |
| `nvt_eburner` | 738,036 | Static ARM32 burner |

`run.sh` is the whole update logic on the script side:

```sh
# lines 3-7
insmod /tmp/sys_run/ndp_preinit.ko
insmod /tmp/sys_run/ndp_gfx.ko ...
# line 11
cp /tmp/sys_run/stty /bin
# lines 16-18
nvt_eburner $1
echo "update finish ,system reboot !!!"
reboot
```

`$1` is the update image path. `nvt_eburner` is a 32-bit ARM EABI5 static
stripped ELF (entry `0x10e11`). It is the only component that writes the eMMC
in the update environment.

## What `nvt_eburner` checks

The binary keeps function names as strings. Three functions carry the trust
checks:

| Function | Address | Evidence |
| :--- | ---: | :--- |
| `nvt_eburner_verify_whole_image` | `0x11ac4` | Reads the 0x120 header, checks magic `TIMG` (`0x474d4954`), hashes the payload in 0x800-byte chunks, compares a 16-byte digest (four words) against the header values. No RSA/SHA calls or strings. |
| Dual-part burn | `0x11434` | For a `DUAL-PART-BURN` component: clears `force_ro` on `/sys/block/mmcblk0boot1/force_ro`, writes with `dd if=%s of=%s bs=1M`, then runs `md5sum` on source and destination and compares. |
| `nvt_eburner_gen_md5tbl_in_ram` | `0x16354` | Reads a `md5tbl` entry, parses colon-separated lines into an in-RAM table, and checks sizes and entries. The source of `md5tbl` is not fully mapped. |

Relevant strings and addresses in `nvt_eburner`:

| String | Address |
| :--- | ---: |
| `DUAL-PART-BURN` | `0x99248` |
| `md5sum %s` | `0x992e8` |
| `# md5sum are not same!! (%s=%s, %s=%s)` | `0x9930c` |
| `PKG_SUCCESS` command | `0x99958` |
| `Set boot part failed` | `0x99870` |
| `md5tbl` | `0x9ae4c` |
| `nvt_eburner_verify_whole_image` | `0x9afdc` |

The update thread is `sub_107e8` (`0x107e8`). It opens the image, reads the
version strings, calls the whole-image verifier, and on success runs
`sub_123ac` (the partition write routine), sets the boot flag
(`sub_12174`), sets the boot partition (`sub_1629c("/dev/mmcblk0", 1, ...)`),
and writes `PKG_SUCCESS` to `/dev/nvt-part-name/misc` at `bs=512 seek=31`
(offset `0x3e00`). On failure it prints `Verify image failed` or
`Invalid image`.

The burner contains no RSA or SHA verify strings. The package acceptance at
this layer is MD5-only. The app layer is different: issue #3 reports
`libfwup.so` with `nvtfw_sec_verify_whole_img_sign`, and
`libmgr_cust.so` checking `autorun.upg` by filename and `md5sum`. Which layer
gates a USB or `/swdl` package is still **OPEN**.

## Live slot map and package matches

`tools/boot_metadata.py` decodes two `PPCH` tables in `p9` (14 entries each,
slot 0 and slot 1). The entries point to the live devices:

```text
vertbl     /dev/nvt-part-name/boot0      offset 0x00e7ee00
xboot      /dev/mmcblk0boot0             offset 0x00000000
stbc_emmc  /dev/mmcblk0boot0             offset 0x000bb800
uboot      /dev/nvt-part-name/boot0      offset 0x00100000
secos      /dev/nvt-part-name/secos0
fdt        /dev/nvt-part-name/fdt0
kernel     /dev/nvt-part-name/ker0
fs         /dev/nvt-part-name/fs0
ap         /dev/nvt-part-name/apexe0
apext      /dev/nvt-part-name/apexe_ext0
```

`p1`/`p2` carry the plaintext `STBC` block at `0x1a0000`, the `UMFG` marker at
`0x1a0200`, and `VTBL` at `0xe7ee00` (length `0x224`). The `VTBL` and `STBC`
bytes are identical in `p1` and `p2`, but they do not match the package
components. The live `VTBL` is generated or updated on the device.

Package-to-live checks:

| Component | Live location | Result |
| :--- | :--- | :--- |
| `pptbl0` | `p9 + 0x400` | byte-identical |
| `pptbl1` | `p9 + 0xa00` | byte-identical |
| `vinfo` | `p9 + 0x1000` | byte-identical |
| `upst` | `p9 + 0x3600` | differs (runtime state) |
| `stbc` | `p1/p2 + 0xbb800` | differs (protected/generated) |
| `vtbl` | `p1/p2 + 0xe7ee00` | differs (generated/updated) |
| `bflag` | `p9` | not found byte-identical |
| `kerupm` | `p21 + 0` | byte-identical for 19,841,096 bytes |

`p21` is a plain arm64 Linux uImage with a valid data CRC, load/entry
`0x02800000`, data size 19,841,032, payload entropy 5.67. The package
`kerupm` matches it. The secure slots (`p1`/`p2`, `p13`–`p18`) have
`data_crc=BAD` and payload entropy near 8.0, consistent with the encrypted or
protected images.

## The update trigger

The live `/swdl` holds a different package:

```text

/swdl/autorun_size.txt   917372175
/swdl/autorun_version.txt 940186113
```

`p9` at `0x3e10` holds the last package name:

```text
_ALL_EU_NT72690_TPN256E_V056.002.127.021_upgrade.pkg
```

The local package used for this analysis is `V056.002.236.191` and 1.53 GB. The
`/swdl` file has a different size and MD5, so it is not the same package. The
`p9` last package name is `V056.002.127.021`, older than the running build, but
the `/swdl` file is not matched to it here. The trigger is not fully mapped:

- USB `autorun.upg` and `/swdl/autorun.upg` are both candidates.
- The app layer checks the filename and runs `md5sum`.
- `libfwup.so` carries an RSA verify symbol. Whether it gates the USB or
  `/swdl` package is **OPEN**.
- The `PKG_SUCCESS` marker is written at `p9 + 0x3e00`, just before the last
  package name at `0x3e10`.

## Dump-only test package

A test package was built locally from the `V056.002.236.191` package. Only the
`sys_run` component changed. The secure components and every other PIMG payload
are byte-identical.

Changes:

- Replace `run.sh` with a dump-only script.
- Keep `ndp_preinit.ko` and `nvt_eburner`; add the static `busybox-armhf`.
- Drop `ndp_gfx.ko` and `stty`; the dump script does not use them.
- Pad the new gzip to the original `sys_run` length (5,176,607 bytes), so the
  component offsets and the container length stay unchanged.
- Update the `sys_run` PIMG MD5 and the TIMG container MD5.

Result:

```text
sys_run gzip          4,409,897 bytes, padded to 5,176,607
sys_run stored MD5    780e61163ebcb9a6aab0941260544aab
container MD5         6c0f7326e68e74e469656ad5ef484492
package SHA-256       ccba5334dfb73816cfb616c89d73d6655d4083c2424378fae53b83b747f4f002
```

The modified `run.sh`:

- loads `ndp_preinit.ko`;
- finds `/media/sda1`, `/media/sdb1`, `/mnt/usb`, or `/tmp/usb`, or mounts
  `/dev/sda1`;
- writes `update-proof.txt` with `id`, `uname -a`, `/proc/cmdline`,
  `/proc/partitions`, the full-device SHA-256 of `/dev/mmcblk0`, and the two
  boot-area hashes;
- writes `mmcblk0boot0.img` and `mmcblk0boot1.img` (8 MiB total);
- does not call `nvt_eburner`;
- reboots.

The full user-area image is not written to the USB. That keeps the test
compatible with a FAT32 update stick and reuses the 2026-11-14 network backup
for the full image.

The package is in `dist/update-test/` (gitignored) and is not committed. It is
a classic `TIMG` package. The app-layer USB verifier rejects it; the direct
`/swdl` staging path skips that verifier. The update environment's own check is
open. The restore gate is proven for same-byte boot areas; the update
environment test still needs the flag mapping and a cold boot.

## What the test would answer

- Whether the update loader accepts a package whose `sys_run` MD5 and container
  MD5 were recomputed.
- Whether the app layer's RSA check rejects the modified package before
  `run.sh` runs.
- Which USB path and filesystem the update environment mounts.
- Whether the update environment can read the eMMC without writing it.

If the loader accepts the package, the proof file and boot-area dumps give a
root update environment and a full-device hash without flashing. If it rejects
the package, no partition was written by `run.sh`, and the app-layer gate is
the next target.
