## Field scan

The owner ran a full 65535-port TCP connect scan from a LAN client and found
eight open ports:

| Port | Service |
| ---: | :--- |
| `1925` | JointSpace HTTP |
| `1926` | JointSpace HTTPS |
| `8883` | MQTT over TLS |
| `9080` | NRDP HTTP |
| `49152` | DLNA |
| `56789` | DIAL |
| `56790` | DIAL device description |
| `58012` | TP Vision ODM TLS |

Observed behavior:

- DIAL `:56789` returned HTTP 200 for `/apps/YouTube`, `/apps/Netflix`, and
  `/apps/AmazonInstantVideo` with `dialVer 2.2`. `:56790/dd.xml` returned the
  `tvdevice` description.
- `:8883` completed TLS 1.2 with `CN=TitanOS TV Server`, issuer
  `CN=Titanos Root CA`, SAN `*.titanos.local`. The certificate expired on
  2026-09-18. MQTT anonymous `CONNECT` was accepted; `SUBSCRIBE` to `#` was
  denied with `0x80`.
- `:58012` completed TLS 1.2 with `CN=2K22_PHP_LINUX`, issuer `SMTVXTVROOT`,
  `O=TPV Technology Limited`, `C=TW`. HTTP probes on this port returned no
  reply.
- `:9080` is an NRDP `2020.1.7.0` catch-all: every GET returned `status=ok`.
  A WebSocket upgrade returned `403`.
- DLNA `:49152` served SCPD descriptions (`/cmr.xml` 200). Control paths such as
  `/cmr_control` and `/device.xml` returned 404.
- `:1925` served `/6/system` without authentication. `/6/powerstate`,
  `/6/audio/volume`, and `POST /6/input/key` returned 403. Only `/6/system` was
  open on the tested paths.
- `:1926` accepted TCP connections but returned no HTTP response without
  pairing credentials.
- `:7788` (Chromium/Opera DevTools) was closed on this unit. The
  `70PUS8108/60` report also had it closed.
- No network entry vector was found.

Compared with the `70PUS8108/60` report in
[research/33](33-tpn236e-70pus8108-network-surface-2026-11-14.md), this unit
has `8883` and `9080` open, uses `49152` instead of `49153`, and has `:7788`
closed. The port surface varies within the family.

The expired `:8883` certificate is recorded as observed. Confirm it on another
`TPN236E` unit before treating it as a build-wide fact.

## Static notes

The contributor's static analysis of `TPN236E_236.006.135.001` found:

- The package is `TIMGPKGVER40` with 19 components. The parser support is
  merged. See [the firmware container](03-firmware-container-timg-pimg-nfsb.md)
  for the layout and the 19-row reference list.
- Every stored component payload is vendor-encrypted. The `PIMG` MD5 covers the
  stored payload. The fixed keys live in `libfwup.so` `.data`.
- `fs` targets `/dev/mmcblk0p16` on this package. Partition numbers are
  firmware-specific; on `TPN256E`, `fs0`/`fs1` are `p19`/`p20`.
- No `quick_debug` chain was found in the decrypted `ap` and `fs` trees
  (grep: 0 hits). `S21idtv.sh` sources the first existing `run_path`; the
  on-board `/mtd_apexe/board/run.sh` wins, so a USB `board/run.sh` is not
  sourced.
- The `customer_env.sh` hook is present in `run.sh:333`, and
  `/swdl/telnet/telnetd` is present in `run_custom_impl.sh:56-58` and
  `:68-70`. These line references are contributor-local.
- `profile_emmc` mounts `mtd_apexe`/`apexe_ext` with an overlayfs upperdir on
  the writable ext4 area, and the `idtv` user owns that RW area.
- SELinux is enforcing. `gdbserver` ships in the application partition.
- The app-layer package check uses `libmgr_cust` by filename and MD5. The RSA
  verifier is in `libfwup`. A modified `autorun.upg` remains unlikely.

The `quick_debug` absence and the OverlayFS layout are `TPN236E` findings, not
platform-wide facts. The `55PUS8000/12` has `quick_debug`
([research/05](05-usb-autorun-hook.md)) and no OverlayFS
([research/18](18-live-inventory-2026-11-09.md)).

## Root-path implication

`idtv` can write the RW area that hosts `customer_env.sh` and the overlay
upperdir. The inferred chain is `idtv` code execution -> RW write -> shipped
hook as root at the next boot. No initial-entry vector is known. Keep this
chain `INFERRED` and out of the documented root path until reproduced.

Physical USB plus cold boot remains the only verified root path on the tested
`55PUS8000/12`.

## Package artifact

The package size is 621,094,116 bytes, reported for a fresh public copy in
issue #5. Two external contributors reported the component list and 19/19
component MD5 result, but the stored-MD5 table and SHA-256 are unpublished.
A derived 19-row offset table is in doc 03; it follows the 0x460 header rule and ends at
`0x250524e4`, but it is not an independent binary parse. The `quick_debug`
grep reported 0 hits; the hook line references are contributor-local. This
note records the static findings as `REPORTED`, not `VERIFIED`.

## Entry-vector assessment

- No root or network entry vector was found. The `:1926` control surface is
  open on this build, but it changes keys and volume and reads state. It does
  not provide a shell, file access, or code execution.
- No known no-network initial-entry path exists for 2023 Titan OS. The `idtv`
  RW-hook chain still needs an initial entry.
- The `:7788` CDP surface was closed on the field unit (`236.006.169.001`,
  issue #6); the `70PUS8108/60` unit also had it closed. Static analysis cannot
  map it, so do not assume it is closed on another build. Do not expose or
  forward CDP.
- Do not expose `:1926` to an untrusted LAN.
