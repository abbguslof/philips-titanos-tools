# 43PUS7608/12 (TPN236E) 236.006.169.001: verified artifact and static follow-up

public download. `:7788` is closed on the default boot and no CDP endpoint was

## Boot-chain findings

### `stbc_emmc` is 8051 code

`stbc_emmc` is a 65,796-byte 8051 image: a 64 KiB flash image plus a 260-byte
trailer. Entry `0x0` clears IRAM, sets `SP=0x51`, and jumps to `0xa047` in the
MCU monitor ROM. The image contains 73 `lcall 0xa62e` monitor calls, XDATA MMIO,
GPIO init/auth, NEC/RC5/RC6 IR decode, UART/IPC, standby power sequencing, ADC,
RTC, and a CPE watchdog. Banner strings include `NVT Monitor`, `Philips FTV`,
`TPV-690-EMMC-20K`, and build `Oct 09 2024 17:22:49`.

The 260-byte trailer carries the signature; the public key is not in the
package. Target: `/dev/mmcblk0boot0` at offset 768,000 (`0xbb800`).

### `xboot` carries an 8051 loader and a second encrypted layer

Inside the decrypted `xboot`, `0x4800-0x4fff` is a plaintext 8051 image: reset
vector `ljmp 0x0086`, IRAM-clear startup, then a `movx` loop copying `0x903e`
bytes from XDATA `0x0100` to `0x9000` after pokes at `0xf17a`/`0xf17c`.
Strings include `einit=>`, `eread=>`, `ecsd=0x`, and `Cmd TO`.

The bulk of `xboot` is not FW40-encrypted plaintext. It is high-entropy at every
granularity (4 KiB entropy 7.954, no compression magic, `len % 16 = 8`), and
the intact zero/`0xff` fill plus the readable 8051 section show the FW40 layer
decrypted correctly. The FWVR-style key derivation and the FW40 keys do not
produce valid padding or an HMAC match on the bulk. The working conclusion is a
second boot-ROM/OTP layer whose key is not derivable from the package. Treat
that as `INFERRED`, not a recovered key. It is consistent with the
`SWType:secure` package flag.

### Update environment

The `169.001` package has no `eburner`, `sys_run`, or `kerupm` components. The
8000 RAM-update environment does not exist here. The 2023 update environment is
`stbc_emmc` plus encrypted `xboot` plus `uboot`; `version_info` reports
`upgrade_xboot:yes`. Do not apply the 8000 eburner/`kerupm` route to this
family.

### FW40 keys in `libfwup.so`

The three FW40 key blobs byte-match the third-party extractor's key file:
`NVT_FW40_IMG_ENC_KEY` (16 B) at `.data+0xc8`, `NVT_FW40_IMG_ENC_V2_KEY`
(32 B) at `.data+0xd8`, and `NVT_FW40_IMG_ENC_IV` (16 B) at `.rodata+0x2280`.
This confirms the doc 03 claim against the binary.

## Live follow-up

### No CDP endpoint

Chromium CDP probes (`/json/version`, `/json`, `/json/list`) against all eight
open ports (`1925`, `1926`, `8883`, `9080`, `49152`, `56789`, `56790`, `58012`)
found no CDP endpoint. `:1925` returns `403` HTML for non-JointSpace paths;
`:1926` returns an empty reply; `:9080` is the `status=ok` catch-all;
`:49152`, `:56789`, and `:56790` return 404; `:58012` is TLS-only. `:1925`
control paths stay `403` with `Origin`/`Referer` spoofing. The
`CDP -> idtv code execution` candidate is closed on the default boot. A
physical USB `nbrowser_log_to_file` flag can enable `:7788` on the next browser
launch; this is a local/physical path, not a remote entry. See
[the corrections note](36-tpn236e-169001-corrections-2026-11-16.md).

### `msg_server` local root `system()` queue

`msg_server` is an 11 KB, 32-bit ARM ELF with debug info, started as root by
`run.sh:512-514`. It calls `ftok("/tmp/msg", 0xff)`, then
`msgget(key, 0x7b6)` (`IPC_CREAT | IPC_EXCL | 0666`). Its loop reads 256 bytes
with `msgrcv(..., msgtyp 0)`, passes `r7+8` directly to `system()`, and posts a
reply with `msgsnd`. There is no command whitelist, prefix, or validation. The
queue is world-writable and `/tmp` is `tmpfs mode=1777`.

Offsets: `ftok` `0x105fa`, `msgrcv` `0x1068e`, `system` `0x106a0`, `msgsnd`
`0x106e4` and `0x10730`.

This is a local privilege-escalation pattern for a process that can send to the
queue. It is not an initial entry vector, and it is not a network entry.
`msg_server` and `cmd_daemon` both carry `idtv_exec_t` in `file_contexts`
(`1336`/`1337`). `msg_server` runs as `initrc_t` because `run.sh` copies it to
`/tmp`; `cmd_daemon` is active via `nvt.app.ini`, not commented out. The
in-firmware senders in `libmid`/`libdev` run as `idtv_t` and are denied
`msg send` by `policy.30`. The factory console in `libmgr_cust` is a local
escalation; private disclosure, no payload. See
[the corrections note](36-tpn236e-169001-corrections-2026-11-16.md).

## Remaining candidates

- Physical serial console, USB-gated CDP, and the factory console. See
  [the corrections note](36-tpn236e-169001-corrections-2026-11-16.md). None is
  remote.
- SAM NVM write to p9 to set `PKG_ready` at `misc+0x3e00`.
- Signed-downgrade diff against `236.006.135.001`, using the doc 03 layout as
  the reference.
- No network entry, no CDP, and no package-resident update-mode command
  execution were found.

## What this means

- The 169.001 artifact is externally verified for the component layout and
  stored integrity. The 135.001 exact artifact hash is still not provided; the
  layout match is not a byte-identity claim.
- The boot chain has another layer: signed 8051 `stbc_emmc`, an 8051 loader in
  `xboot`, and an OTP/ROM-encrypted `xboot` bulk. This reinforces the Level 4
  block; the package does not contain a reachable boot update code path.
- The CDP route to `idtv` is closed on this family. `msg_server` is a local
  root shortcut only after `idtv` execution exists; it does not create the
  initial entry.
- At the time of this note, Level 3.5 still needed the reusable `ndp_logo`
  carrier. That carrier is now verified (2026-11-20; see
  [doc 37](37-kernel-carrier-level-3-5.md)). This note does not add a network
  or package entry vector.
