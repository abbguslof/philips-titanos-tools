## `p1` / `p2` slot markers

The two 24 MiB vendor boot slots are identical except two bytes:

| Offset | `p1` | `p2` |
| :--- | :--- | :--- |
| `0x1a0034` | `0x55` | `0x13` |
| `0x1a0204` | `0x00` | `0x01` |

`UMFG` is at `0x1a0200`; `0x1a0204` is its slot byte. At `0x100000` is the
encrypted U-Boot/FIT segment (468,137 bytes). At `0x1a0000` is a plaintext
`STBC` boot-control block; the `UMFG` slot sits inside it. At `0xe7ee00` is a
`VTBL` verification table (`0x224` bytes, signature/hash blob); it is identical
in both slots. The `ATF` string appears at `0x129c12` inside the encrypted
U-Boot segment. The `PPCH` table points `vertbl` at `0xe7ee00` and `uboot` at
`0x100000`.

## `p9` metadata

`p9` starts with `DBFG` and contains plaintext structures:

| Offset | Magic | Meaning |
| ---: | :--- | :--- |
| `0x0` | `DBFG` | partition metadata header |
| `0x400`, `0xa00` | `PPCH` | partition-control tables |
| `0x1000` | `FWVR` | `TPN256E_V056,rev:191,...` model record |
| `0x1200`, `0x2400` | `NVHC` | boot-area 0/1 hash/partition tables |
| `0x3600` | `UPST` | update/upgrade state |
| `0x3e10` | n/a | last package name (`...V056.002.127.021...`) |

Each `PPCH` entry is 60 bytes: name (16), device (32), offset (4), flag (4),
slot (4). The first table is slot 0; the second is slot 1. The first table resolves `uboot` to offset `0x100000` and `vertbl` to
`0xe7ee00` inside `p1/p2`, and maps `secos`/`fdt`/`kernel`/`fs`/`apex` to the
`secos0`/`fdt0`/`ker0`/`fs0`/`apexe0` devices.

The `NVHC` tables repeat the slot map for `emmc_boot0/1`, including
`secos0/1`, `ker0/1`, `fdt0/1`, `fs0/1`, `apexe0/1`, `apexe_ext0/1`,
`bflag`, and `misc`. The first `NVHC` entry carries an XBoot hash beginning
`c0358135...`. These are hash/partition maps, not a private key.

The normal A/B path is `secos0/1 -> fdt0/1 -> ker0/1 -> fs0/1`. The plain
`p21` kernel is not in that `kernel`/`ker` map; it is outside the normal A/B
boot map and is likely a recovery/legacy image.

differ from the package templates because they are runtime/state records; the
live `bflag` was not found byte-exact.

## Update environment

The package also contains the RAM update environment:

| Component | Shape | Target |
| :--- | :--- | :--- |
| `eburner` | plain Linux/arm64 uImage, 22,566,984 | `/dev/null` |
| `sys_run` | gzip tar, 5,176,607 (19,005,440 unpacked) | `/dev/null` |
| `nvt_eburner` | static ARM32 ELF, 721 KiB, inside `sys_run` | update rootfs |

`sys_run/run.sh` runs `nvt_eburner $1` after loading the two kernel modules.
`nvt_eburner` contains MD5 verification and partition-write logic; its strings
show `nvt_eburner_verify_whole_image`, `nvt_eburner_md5_part_verify`,
`md5sum`, `md5tbl`, and `Verify image failed`, but no RSA/SHA strings were
observed. `eburner`, `sys_run`, `nvt_eburner` and `kerupm` are plain at the
component level; the package container/PIMG checks are MD5-only; the NFSB
filesystems remain signed.

The update environment is a potential update-mode code-execution path. The
controlled test is a modified `sys_run/run.sh` that only dumps the eMMC
and boot areas to USB and skips `nvt_eburner`; it must be tested only after the
eMMC/recovery gate. See [update package map](../../docs/research/29-update-package-map.md).

## Interpretation

- The secure A/B chain is intact and encrypted.
- The eMMC boot areas are identical and write-protected; there is no ready
  second boot slot.
- `p21` is the only plain executable boot image. It may be a vendor
  legacy/recovery kernel. Its boot selection and verification policy are the
  next target.
- No boot writes were made. NVM, pstore, and boot slots remain local-only.
